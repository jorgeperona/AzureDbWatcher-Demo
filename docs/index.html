LA SESIÓN / DIAPOSITIVAS 5–11

Database watcher.
De las consultas a la visibilidad.

El contenido de la presentación, adaptado a la web: qué monitoriza, cómo recopila los datos y qué necesitas para conectarlo.

06 / QUÉ ES · PREVIEW

Una vista unificada de tu entorno Azure SQL

Una solución administrada de monitorización para consultar la configuración, el estado y el rendimiento de Azure SQL Database y Azure SQL Managed Instance.

  • Azure SQL Database: bases de datos individuales, elastic pools e Hyperscale.
  • Réplicas: secundarias de solo lectura y alta disponibilidad, georréplicas y named replicas de Hyperscale, según el tipo de destino compatible.
  • Visualización: paneles unificados y análisis personalizados con Power BI o Grafana sobre los datos recopilados.
  • Alcance de la presentación: Azure Arc y SQL Server en máquinas virtuales se mencionan como posibilidades futuras, no como soporte disponible ni comprometido.
07 / ARQUITECTURA

Tres piezas, un flujo de datos

  1. 01 / SQL TARGETS

    Los destinos

    Bases de datos, pools e instancias que quieres monitorizar.

  2. 02 / WATCHER

    El recopilador remoto

    Ejecuta consultas T-SQL sobre más de 70 vistas de catálogo y DMV. Transforma los resultados en datasets.

  3. 03 / DATA STORE

    El almacén analítico

    Azure Data Explorer o Real-Time Analytics de Microsoft Fabric. Almacena y permite analizar los datasets con KQL.

08 / LÍMITES Y REQUISITOS

Planifica antes de conectar

  • Watcher, destinos y almacén deben pertenecer al mismo tenant de Microsoft Entra ID.
  • Comprueba las regiones disponibles durante la preview.
  • 20 watchers por suscripción y hasta 100 SQL targets por watcher, según la documentación consultada.
  • Las réplicas monitorizadas cuentan como destinos independientes.

Aclaración de la diapositiva: no se necesita un watcher por destino. Un watcher puede recopilar datos de múltiples SQL targets. Los límites de preview pueden cambiar.

09 / COSTES

El watcher es gratuito.
Su entorno puede no serlo.

  • Sin coste por watcher ni por los dashboards del servicio.
  • Presupuesta el data store: Azure Data Explorer o la capacidad y el consumo de Fabric.
  • En la misma región no se añade el coste de transferencia entre regiones; en regiones distintas puede haber tráfico de salida facturable.
  • También pueden aplicar costes de Key Vault y de las alertas configuradas.

El mensaje «solo pagas el datastore» de la presentación es una simplificación: revisa todos los componentes de tu despliegue.

10 / CONECTIVIDAD

Pública o privada.
Siempre controlada.

  • Pública: reglas de firewall basadas en IP para permitir la conexión.
  • SQL Managed Instance: habilita el endpoint público y configura la regla NSG de entrada TCP 3342 con origen AzureCloud, si usas esta modalidad.
  • Privada: managed private endpoints hacia los SQL targets; esta ruta tiene prioridad cuando está configurada.
  • También puedes usar conectividad privada con Azure Data Explorer para proteger el recorrido hasta el almacén.

La conectividad no concede permisos SQL. El responsable del entorno controla tanto la red como el acceso a los datos de monitorización.

11 / IDENTIDAD Y PERMISOS

Acceso específico.
Privilegios limitados.

Microsoft Entra ID: el watcher usa su identidad administrada para iniciar sesión. Como alternativa, la autenticación SQL utiliza credenciales almacenadas en Key Vault.

En Azure SQL Database, la identidad necesita estos roles de servidor:

  • ##MS_ServerPerformanceStateReader##
  • ##MS_DefinitionReader##
  • ##MS_DatabaseConnector##

SQL Managed Instance requiere un conjunto distinto de permisos. El watcher valida el acceso y puede desconectarse si faltan permisos o sobran privilegios; no le concedas acceso general a datos de negocio.

Material de la sesión, no una promesa de disponibilidad. La presentación describe Database watcher en preview. Microsoft anuncia su retirada para el 30 de abril de 2027 y la transición a Database Hub en Microsoft Fabric. Consulta el estado del servicio, los límites y los costes actuales antes de preparar el entorno.

LA SESIÓN / DIAPOSITIVAS 12–15

Azure SRE Agent.
De la señal a la investigación.

Tu compañero de operaciones con IA: conecta recursos, observabilidad y plataformas de incidentes para ayudar al equipo a mantener la fiabilidad.

13 / TU ASISTENTE DE FIABILIDAD

Menos trabajo repetitivo. Más contexto para decidir.

Investiga, correlaciona señales y ayuda a diagnosticar problemas de producción con supervisión humana y límites de gobernanza. El objetivo: reducir el tiempo de recuperación (MTTR), la fatiga de alertas y el trabajo operativo repetitivo (toil).

  1. 01

    Detecta

    Responde a alertas de Azure Monitor o de plataformas conectadas como PagerDuty y ServiceNow.

  2. 02

    Diagnostica

    Correlaciona logs, métricas, trazas y despliegues recientes para buscar causas con evidencias.

  3. 03

    Mitiga

    Propone acciones o las ejecuta según el modo de revisión o autónomo, los permisos y las políticas.

  4. 04

    Aprende

    Conserva el contexto de investigaciones anteriores para ayudar ante incidentes similares.

La respuesta automatizada puede estar disponible ante alertas en cualquier momento. El agente no sustituye a la instrumentación ni a la monitorización continua de un APM.

14 / QUÉ HACE

Capacidades para investigar y actuar

Diagnóstico en lenguaje natural

Descríbele el incidente: consulta las herramientas conectadas, ejecuta comandos autorizados y cruza logs y métricas para presentar evidencias.

Análisis de causa raíz

Ante un CrashLoopBackOff, puede revisar logs, eventos, límites de recursos, imagen y sondas de readiness en lugar de quedarse en el síntoma.

Remediación guiada

Propone acciones y comandos. En modo Revisión solicita aprobación; en modo Autónomo puede actuar sin esperarla, dentro de los permisos y límites configurados.

Code Interpreter

Ejecuta Python para analizar datos y generar entregables como informes PDF, gráficos, libros de Excel, dashboards y exportaciones, según las herramientas disponibles.

Automatización recurrente

Programa chequeos de salud, revisiones de seguridad o validaciones posteriores al despliegue, con registro y notificaciones configuradas.

Memoria operativa

Reutiliza el historial y el conocimiento registrado: qué falló, qué funcionó y qué causa se identificó. No equivale a garantizar un diagnóstico correcto.

15 / QUÉ NO HACE

Un asistente, no un sustituto del equipo

  • No reemplaza a tus ingenieros. El equipo mantiene la responsabilidad operativa y define la gobernanza.
  • No ejecuta acciones destructivas sin aprobación en modo Revisión. El modo Autónomo tiene un comportamiento distinto: configura sus permisos y políticas con cuidado.
  • No monitoriza 24/7 como un APM. Se activa por chat, alertas o tareas programadas y utiliza las señales que proporcionan las herramientas conectadas.
  • No conoce tu lógica de negocio de forma nativa. Necesita contexto, una base de conocimiento y, cuando proceda, subagentes especializados.

Las capacidades dependen de la configuración, las integraciones y la disponibilidad del servicio. Explorar Azure SRE Agent en Microsoft Learn →

HAZLO TÚ

De cero a tu primer bloqueo.

Una base de datos de pruebas. Varias conexiones. Una pregunta: ¿qué está esperando?

  1. Prepara el terreno

    Usa una base de datos aislada, SSMS o VS Code con MSSQL y permisos para crear objetos. Configura Database watcher antes de empezar: estos scripts no despliegan recursos ni monitorización.

    Consultar requisitos →

  2. Crea tablas y procedimientos

    Confirma el destino y prepara el esquema SalesLT. Ejecuta primero el script combinado de tablas y después el de procedimientos. Crear tablas elimina sus datos anteriores.

    Preparar la base de datos →

  3. Abre dos conexiones independientes

    Ejecuta A y, antes de que termine, ejecuta B en la misma base de datos.

    CONEXIÓN A
    EXEC SalesLT.GenerateLongBlock
  @Id = 1, @HoldSeconds = 30;
    CONEXIÓN B
    EXEC SalesLT.TryAccessBlockedRow
  @Id = 1;

  4. Observa la señal y cierra el círculo

    Desde una tercera conexión, correlaciona sesiones y esperas con la monitorización. B suele agotar su espera en unos cinco segundos: un timeout no es un deadlock. Repite B cuando termine A y compara.

    Detener y restablecer con seguridad →
!

Rompe cosas. Pero solo en el laboratorio.

Estas pruebas modifican datos, pueden dejar transacciones abiertas y generar costes. Empieza con poca carga, registra una línea base y comprueba las conexiones al terminar. No uses producción. Los planes JMeter pueden insertar filas y requieren sus propias tablas de ejemplo.
